# Roadmap and known gaps

This tracks work that was deliberately scoped out of the current release, so it isn't lost and isn't silently rediscovered later. Nothing here is scheduled; each item is a candidate, not a commitment. For registry/directory submissions (Official MCP Registry, Glama, PulseMCP, Smithery, mcp.so, Awesome MCP lists, Docker MCP Catalog), see the "Phase 2" section of [RELEASE_CHECKLIST.md](RELEASE_CHECKLIST.md) — that checklist is the single source of truth for publication steps and isn't duplicated here.

## Connection compatibility expansion (auth, charset, TLS)

Not implemented. This project intentionally ships with driver defaults only: no `insecureAuth`, no charset override, no TLS. See the "no `MYSQL_LEGACY_INSECURE_AUTH`, `MYSQL_LEGACY_CHARSET`, or `MYSQL_LEGACY_SSL`" note in [CONFIGURATION.md](CONFIGURATION.md) and the TLS/charset claim boundaries in [AUDIT.md](AUDIT.md).

If this is picked up later, it covers three separate sub-problems, none of which should be assumed to transfer to the others:

1. **Pre-4.1 `old_password` authentication / `insecureAuth`.** Every MySQL version reachable in this project's live-test matrix (5.0.51a and up) already defaults to post-4.1 `mysql_native_password`, so this is genuinely unverified, not just undocumented. Proving it needs an actual MySQL 3.x/4.0 build, or a 5.0 server explicitly reconfigured with `old_passwords=1` — both out of scope for the current live-test setup. A label like "old_password supported" must not ship until a real server on that auth path has been exercised end-to-end through the MCP tools, not just through the driver directly.
2. **Configurable connection charsets** (`cp1251`, `latin1`, and one non-Unicode charset outside Cyrillic locales, e.g. `sjis`). The driver currently connects with its default `UTF8_GENERAL_CI` and avoids requesting `utf8mb4`. For plain reads this is usually not a problem on its own — MySQL converts a table's storage charset to the connection's requested charset on the fly, and that conversion works cleanly for cp1251/latin1 Cyrillic or Western text read through the default `UTF8_GENERAL_CI` connection (confirmed against a live cp1251 production table). The real gaps a configurable charset would close are: (a) **write-path safety** — `mysql_legacy_insert`/`_update` have no guard today against text containing characters outside a target column's charset repertoire, which can silently mangle or reject on write; (b) **recovering already-mojibake'd legacy data**, where auto-conversion can't fix bytes that were wrong before this tool ever touched them, and reading the raw bytes back (deliberately connecting under a different charset) is sometimes the only way to re-decode them correctly; (c) **`utf8mb4` support**, a related but distinct gap — any table that actually stores 4-byte Unicode (emoji, some CJK) will have both reads and writes mangled through the current 3-byte connection charset. As a cheap first step (shipped 2026-09-10, no connection-charset change), `mysql_legacy_describe_table` now returns each column's `collation` and `mysql_legacy_show_create_table` returns the table's parsed `charset`, so an agent can see the risk before writing without implementing any of the above.
3. **TLS/SSL for legacy deployments.** Old MySQL servers' OpenSSL stacks frequently can't negotiate with a current Node.js TLS stack. This needs testing both a successful verified-TLS path and a rejected-invalid-certificate path, and must not globally weaken Node's TLS policy to paper over a negotiation failure. If a given old server genuinely can't negotiate securely, the honest answer is to document that and recommend a local secure tunnel — not to silently loosen defaults.

Ground rules for whichever of these gets picked up: keep every new behavior opt-in (never on by default), validate every new environment variable, never log credentials/certificate contents/private keys, and add MCP-level integration tests (driving the real server over stdio, not just calling the driver directly) before updating any claim in README/CONFIGURATION/TROUBLESHOOTING/AUDIT. A compatibility claim without a passing test against a real server on that path is not a compatibility claim — it's a guess, and this project's documentation is expected to say so explicitly rather than round up.

## Write-operation configuration granularity not built in this round

The four opt-in write tools (`mysql_legacy_insert`/`_update`/`_delete`/`_ddl`) ship with an intentionally narrow configuration surface, modeled on `benborla/mcp-server-mysql`'s flags but with several of its options deliberately left out for a niche, low-traffic tool. None of these are hard to add later; they were skipped because the cost (new config surface, more to test, more to document) didn't clear the bar for this project's "golden mean" of usefulness vs. complexity:

- **Multi-database write control / per-schema permission overrides** (the equivalent of benborla's `MULTI_DB_WRITE_MODE` and `SCHEMA_INSERT_PERMISSIONS`/`SCHEMA_UPDATE_PERMISSIONS`/`SCHEMA_DELETE_PERMISSIONS`/`SCHEMA_DDL_PERMISSIONS`). This solves "one MCP server, many databases with different trust levels" — a multi-tenant SaaS scenario this project doesn't target. `MYSQL_LEGACY_DATABASE` here is a single optional default, and the expected user is one engineer against one legacy production database. Revisit only if real users ask for per-database write policy.
- **Rate limiting and query-complexity scoring** (`MYSQL_RATE_LIMIT`, `MYSQL_QUEUE_LIMIT`, `MYSQL_MAX_QUERY_COMPLEXITY` equivalents). Would require persistent in-process counters and a nontrivial AST-based complexity scorer. Not worth it for a tool an AI agent calls occasionally, not a high-throughput service.
- **Pool `acquireTimeout`** (how long a caller waits for a free pooled connection before failing). Only `MYSQL_LEGACY_POOL_SIZE` and `MYSQL_LEGACY_CONNECT_TIMEOUT` were exposed as new knobs when the pool was added; `acquireTimeout` stays at the `mysql` driver's default (10s). Add it as a config option if pool exhaustion turns out to be a real problem in practice.
- **`mysql_legacy_ddl` beyond table-level statements.** It currently only accepts `CREATE TABLE`, `ALTER TABLE`, `DROP TABLE`, `TRUNCATE TABLE`, and `RENAME TABLE`; `DROP DATABASE`, `CREATE`/`DROP VIEW`, `CREATE`/`DROP INDEX`, and similar are rejected. This was a deliberate scope-narrowing decision (every other tool in this server targets a single `database.table` pair; `DROP DATABASE` behind one generic flag is a much larger blast radius than anything else exposed here). Loosening this should be a specific, explicit decision, not an incidental side effect of a refactor.
